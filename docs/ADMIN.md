# SAVAR — административная панель

## Статус документа

Рабочая спецификация.

Документ развивается вместе с SAVAR. Новые административные
возможности сначала фиксируются здесь, а затем реализуются
в административной панели.

Не следует заранее проектировать функции, необходимость которых
ещё не возникла в пользовательской части SAVAR.


---

# 1. Назначение

Административная панель SAVAR — внутренний рабочий интерфейс
VKazakDon Studio.

Она предназначена для управления системой, клиентами, проектами
и работами, которые клиенты передают VKazakDon Studio.

Административная панель:

- не является кабинетом клиента;
- не является кабинетом стороннего исполнителя;
- не является маркетплейсом исполнителей;
- используется VKazakDon Studio для внутренних рабочих процессов.


---

# 2. Основной принцип

Клиент взаимодействует с VKazakDon Studio.

Для клиента исполнителем переданной работы всегда является:

**VKazakDon Studio**

Фактически работу внутри студии в будущем может выполнять:

- владелец студии;
- сотрудник;
- привлечённый специалист;
- подрядчик.

Это внутреннее распределение работы.

Привлечённый специалист или подрядчик не становится отдельным
исполнителем клиента SAVAR.

Ответственность за работу перед клиентом остаётся на
VKazakDon Studio.


---

# 3. Предварительная структура админки

По мере развития SAVAR административная панель может включать:

- Обзор;
- Клиенты;
- Проекты;
- Задачи студии;
- Диагностика;
- Услуги;
- Настройки.

Это не окончательная структура.

Разделы добавляются и уточняются по мере появления реальной
необходимости в клиентской части системы.


---

# 4. Задачи студии

## 4.1. Назначение

Раздел «Задачи студии» предназначен для работы с задачами,
которые клиенты SAVAR передали VKazakDon Studio.

На текущем этапе задача попадает сюда из:

**Проект → Диагностика → План работ**

После обнаружения проблемы клиент добавляет её в план проекта
и выбирает способ выполнения:

- Самостоятельно;
- Поручить VKazakDon Studio.

При выборе:

**Поручить VKazakDon Studio**

задача становится доступна административной части системы.


---

# 5. Данные задачи студии

Минимально задача должна содержать:

- идентификатор задачи;
- идентификатор проекта;
- проект;
- клиент;
- название задачи;
- описание проблемы;
- рекомендацию;
- приоритет;
- источник задачи;
- способ выполнения;
- текущий статус;
- дату передачи студии.

Для задачи, созданной по результатам диагностики, необходимо
сохранять связь с соответствующим результатом диагностики.


---

# 6. Способ выполнения

Для клиентского плана предусмотрены два основных значения:

```text
self
studio

self

Задачу выполняет клиент самостоятельно.

studio

Задача передана на выполнение VKazakDon Studio.

Старое значение:

executor

не используется.

7. Жизненный цикл задачи VKazakDon Studio

Базовый жизненный цикл:

Передана студии
        ↓
Принята студией
        ↓
В работе
        ↓
Завершена

Технические значения:

studio-pending
studio-accepted
in-progress
completed
8. Передана студии

Технический статус:

studio-pending

Статус устанавливается после того, как клиент выбирает:

Поручить VKazakDon Studio

В этот момент задача ещё не считается принятой студией
и не считается находящейся в работе.

В клиентском кабинете отображается:

Передана студии

Административная панель должна показать такую задачу среди
новых поступивших задач.

9. Принята студией

Технический статус:

studio-accepted

Статус устанавливается со стороны административной панели
VKazakDon Studio.

Он означает:

студия увидела задачу;
задача принята;
студия подтверждает дальнейшую работу с ней.

В клиентском кабинете отображается:

Принята студией

На этом этапе работа ещё не обязательно начата.

10. В работе

Технический статус:

in-progress

Статус устанавливается со стороны административной панели.

Он означает, что фактическое выполнение задачи началось.

В клиентском кабинете отображается:

В работе

11. Завершена

Технический статус:

completed

Статус устанавливается после завершения работы студией.

В клиентском кабинете отображается:

Работа завершена

В дальнейшем завершение задачи может сопровождаться:

описанием выполненной работы;
результатом;
файлами;
ссылками;
комментарием студии;
датой завершения.

Эти возможности пока не реализуются.

12. Действия VKazakDon Studio
Для задачи «Передана студии»

Административное действие:

Принять задачу

Переход:

studio-pending
→
studio-accepted
Для задачи «Принята студией»

Административное действие:

Начать работу

Переход:

studio-accepted
→
in-progress
Для задачи «В работе»

Административное действие:

Завершить работу

Переход:

in-progress
→
completed
13. Права клиента

Клиент может:

добавить результат диагностики в план;
выбрать самостоятельное выполнение;
передать задачу VKazakDon Studio;
видеть текущий статус студийной задачи;
изменить способ выполнения, пока это разрешено состоянием задачи;
отложить задачу, пока это разрешено состоянием задачи;
в дальнейшем получить результат работы студии.

Клиент не может:

принять задачу от имени VKazakDon Studio;
самостоятельно установить статус «Принята студией»;
самостоятельно перевести студийную задачу в работу;
завершить задачу от имени студии;
назначить внутреннего сотрудника или подрядчика студии.
14. Внутренний исполнитель

В будущем административная панель может позволить назначить
внутреннего исполнителя задачи.

Внутренним исполнителем может быть:

владелец VKazakDon Studio;
сотрудник;
привлечённый специалист;
подрядчик.

Это внутреннее поле административной системы.

Клиентская модель выполнения при этом не изменяется:

executionMode: studio

То есть добавление сотрудников или подрядчиков не должно
потребовать изменения клиентского плана SAVAR.

15. Внутренняя информация

В дальнейшем у задачи могут появиться данные, доступные только
VKazakDon Studio:

внутренний ответственный;
исполнитель;
внутренний комментарий;
оценка трудоёмкости;
внутренняя стоимость;
планируемый срок;
фактический срок;
внутренние вложения.

Эти данные не должны автоматически становиться доступными
клиенту.

16. Клиентская информация

Отдельно могут храниться данные, предназначенные для клиента:

согласованная стоимость;
согласованный срок;
комментарий студии;
состояние работы;
результат работы;
клиентские вложения;
итоговые файлы.

Внутренние и клиентские данные задачи необходимо разделять.

17. История задачи

В дальнейшем необходимо предусмотреть журнал изменений задачи.

Пример событий:

14.08.2026  Клиент передал задачу студии
14.08.2026  VKazakDon Studio приняла задачу
15.08.2026  Работа начата
16.08.2026  Работа завершена

Для события желательно хранить:

тип события;
дату и время;
инициатора;
старое состояние;
новое состояние;
комментарий при наличии.

История должна формироваться системой, а не храниться только
как произвольный текст.

18. Будущая стоимость работ

Стоимость пока не реализуется.

Архитектура задачи должна позволять в дальнейшем добавить:

предварительную оценку;
согласованную стоимость;
состояние согласования;
состояние оплаты;
способ оплаты;
историю изменений стоимости.

Не следует смешивать внутреннюю оценку студии и стоимость,
показанную клиенту.

19. Будущие сроки

В дальнейшем задача может содержать:

предполагаемую дату начала;
предполагаемый срок выполнения;
согласованный дедлайн;
фактическую дату начала;
фактическую дату завершения.

Сроки пока не являются частью текущей реализации.

20. Фильтрация задач студии

При реализации раздела «Задачи студии» необходимо предусмотреть
как минимум состояния:

Новые;
Принятые;
В работе;
Завершённые.

В дальнейшем могут появиться:

отложенные;
ожидающие согласования;
ожидающие оплаты;
просроченные.

Не реализовывать дополнительные состояния до появления
соответствующей бизнес-логики.

21. Связь с проектом

Каждая студийная задача должна оставаться связанной с проектом.

Из административной панели должно быть возможно перейти:

Задача
→
Проект
→
Клиент

Из проекта в дальнейшем должна быть доступна история всех
связанных с ним работ.

22. Связь с диагностикой

Если задача была создана из результата диагностики, связь
с диагностикой должна сохраняться.

Это позволит в дальнейшем:

открыть исходную проблему;
сравнить состояние до и после работы;
повторно провести проверку;
подтвердить устранение проблемы.

Завершение работы и подтверждение устранения проблемы —
разные события.

Например:

Работа завершена
        ↓
Повторная диагностика
        ↓
Проблема устранена

Это различие необходимо сохранить в архитектуре.

23. Уведомления

В дальнейшем изменение значимых статусов может создавать
уведомление клиенту.

Например:

задача принята студией;
работа начата;
требуется действие клиента;
работа завершена.

Механизм уведомлений пока не реализуется.

24. Безопасность

Административные операции должны быть доступны только
авторизованным пользователям с соответствующими правами.

Клиентский интерфейс не должен иметь возможность выполнить
административный переход статуса простой подменой данных
на frontend.

После появления backend все изменения административных
статусов должны проверяться сервером.

25. Текущая реализация

На текущем этапе реализована клиентская часть плана работ.

Поддерживаются:

добавление результатов диагностики в план;
выбор способа выполнения;
самостоятельное выполнение;
передача задачи VKazakDon Studio;
отображение статуса студийной задачи;
подготовленная модель статусов студии.

Текущий жизненный цикл самостоятельной задачи:

Новая
→
Запланирована
→
В работе
→
Завершена

Текущая модель студийной задачи:

Передана студии
→
Принята студией
→
В работе
→
Завершена

Клиентская часть уже умеет отображать эти состояния.

Административная панель пока не реализована.

26. Правило развития документа

При появлении новой функции SAVAR необходимо определить:

Требует ли она административного управления.
Какие данные должна видеть VKazakDon Studio.
Какие данные должен видеть клиент.
Какие действия доступны каждой стороне.
Требуются ли новые статусы.
Требуется ли история изменений.
Требуются ли новые административные экраны.

После этого соответствующее описание добавляется в этот
документ.

Реализация административной панели должна опираться на
зафиксированную здесь бизнес-логику, а не дублировать её
отдельными несогласованными правилами.
